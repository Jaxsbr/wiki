# Open Knowledge Format (OKF)

> An open specification by Google Cloud (v0.1, June 2026) that formalizes the [LLM Wiki pattern](llm-wiki-pattern.md) into a portable, interoperable format. Vendor-neutral, agent- and human-friendly standard for representing metadata, context, and curated knowledge.

## What problem it solves

In most organizations, the information AI models need is internal knowledge: table schemas, the business meaning of a metric, incident runbooks, join paths between systems, API deprecation notices. These atoms of knowledge live in fragmented systems:

- Metadata catalogs with their own proprietary APIs
- Wikis, third-party tools, or shared drives
- Code comments, docstrings, notebook cells
- The heads of a few senior engineers

When an AI agent needs to answer "How do I compute weekly active users from our event stream?" it must assemble the answer from scattered, mutually incompatible surfaces. Every catalog vendor reinvents the same data models. The knowledge is locked behind whichever surface created it.

**The result:** Every agent builder solves the same context-assembly problem from scratch. Every wiki produced using the LLM Wiki pattern looks alike (markdown, frontmatter, cross-links) but isn't designed to cooperate. There is no agreed-upon answer to *what fields every document should carry* or *what filenames mean what*.

**What's missing is a format, not another service.** A way to represent knowledge that:

- Anyone can produce, without an SDK
- Anyone can consume, without an integration
- Survives moving between systems, organizations, and tools
- Lives in version control alongside the code it describes
- Is readable by humans *and* parseable by agents — same file, no translation layer

## Design principles

**1. Minimally opinionated.** OKF requires exactly one thing of every concept: a `type` field. Everything else — what types exist, what other fields to include, what sections the body has — is left to the producer. The spec defines the *interoperability surface*, not the content model.

**2. Producer/consumer independence.** OKF cleanly separates *who writes the knowledge* from *who consumes it*. A bundle hand-authored by a human can be consumed by an AI agent. A bundle generated by a metadata export pipeline can be browsed in a visualizer. A bundle synthesized by one LLM can be queried by another. The format is the contract; the tooling at each end is independently swappable.

**3. Format, not platform.** OKF is not tied to any specific cloud, database, model provider, or agent framework. It will never require a proprietary account or SDK to read, write, or serve. Published as an open standard because the value of a knowledge format comes from how many parties speak it, not from who owns it.

## How it works

An OKF **bundle** is a directory of markdown files. Each file represents one **concept** — anything you want to capture: a table, a dataset, a metric, a playbook, a runbook, an API. Each concept is one file. The file path is the concept's identity:

```
sales/
└── weekly_active_users.md
```

Each concept document has:
- A small block of **YAML front matter** for structured fields
- A **markdown body** for everything else

```markdown
---
type: table
title: Weekly Active Users
description: One row per completed customer order.
resource: https://console.cloud.google.com/bigquery?p=acme&d=sales&t=orders
tags: [sales, metrics, core]
timestamp: 2026-05-28T14:30:00Z
---

| Column        | Type      | Description                              |
|---------------|-----------|------------------------------------------|
| `order_id`    | STRING    | Globally unique order identifier.        |
| `customer_id` | STRING    | FK to [customers](/tables/customers.md). |

Joined with [customers](/tables/customers.md) on `customer_id`.
```

Concepts link to each other with **normal markdown links**, turning the directory into a graph of relationships richer than the parent/child hierarchy implied by the file system.

Bundles may optionally include:
- **index.md** files for progressive disclosure as agents navigate the hierarchy
- **log.md** files for chronological history of changes

The full v0.1 specification (conformance criteria, cross-linking rules, reserved filenames) fits on a single page. See [concepts/okf-bundle](../concepts/okf-bundle.md) for the complete anatomy.

## YAML frontmatter fields (v0.1)

| Field | Required | Purpose |
|---|---|---|
| `type` | **yes** — the only required field | What kind of concept this is (table, metric, runbook, etc.) |
| `title` | no | Human-readable name |
| `description` | no | One-line summary |
| `resource` | no | External URL (e.g. BigQuery table URL, API endpoint) |
| `tags` | no | Array of strings for filtering |
| `timestamp` | no | ISO-8601 last-modified timestamp |

Everything beyond these six fields is the producer's choice — domain-specific extensions are explicitly welcomed.

## What Google shipped with the spec

**Reference implementations** — to make the format concrete and lower the cost of trying it:

- **Enrichment agent** — walks a BigQuery dataset, drafts an OKF concept document for every table and view, then runs a second LLM pass that crawls authoritative documentation and enriches each concept with citations, schemas, and join paths.
- **Static HTML visualizer** — turns any OKF bundle into an interactive graph view in a single self-contained file. No backend, no install, no data leaves the page.
- **Three sample bundles** — GA4 e-commerce, Stack Overflow, and Bitcoin public datasets; produced by the reference agent, committed to the repo as conformant OKF examples.

These are **proofs of concept, deliberately.** The agent demonstrates one way to produce OKF; the format requires no specific agent framework or LLM. The visualizer demonstrates one way to consume it; the format requires no HTML or graph view.

Google also updated **Google Cloud Knowledge Catalog** to ingest OKF and serve it to agents.

## Relation to the LLM Wiki pattern

OKF takes [Karpathy's LLM Wiki gist](llm-wiki-pattern.md) from "here is a pattern worth following" to "here is a format anyone can implement and interoperate with." The structural elements map directly:

| LLM Wiki concept | OKF equivalent |
|---|---|
| Raw sources | Producer-generated input (stays outside the bundle) |
| Wiki (markdown pages) | OKF bundle (markdown concepts with frontmatter) |
| Schema (CLAUDE.md) | OKF spec + producer-defined type vocabulary |
| index.md | Optional index.md files per directory |
| log.md | Optional log.md file at root |
| Cross-links | Standard markdown links between concept files |

The key addition OKF makes: **interoperability**. Karpathy's wiki and your team's wiki and a vendor's catalog export can now intentionally cooperate. The spec answers "what fields every document should carry" with the minimum possible answer (just `type`) and leaves the rest to producers — which is what makes it adoptable across heterogeneous organizations.

## Relation to this wiki (ver-kyker)

ver-kyker's wiki already implements the structural core of OKF:
- Markdown files in a directory hierarchy (`topics/`, `concepts/`)
- An `index.md` catalog updated on every ingest
- A `log.md` append-only activity record
- Cross-links via relative markdown links
- A schema (CLAUDE.local.md) governing the LLM's maintenance behavior

To become fully OKF-conformant, ver-kyker would need to:
1. Add YAML frontmatter with `type` to every concept file
2. Follow OKF's cross-linking rules (relative paths, not absolute)
3. Align reserved filenames (`index.md`, `log.md`) — already done

See [multi-product-wiki-architecture](multi-product-wiki-architecture.md) for how OKF enables the system Jaco described: a single agent wiki spanning many products with entry points for external content producers.
